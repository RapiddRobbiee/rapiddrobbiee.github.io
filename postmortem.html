⏱️ The Spiral of Incorrect Guesses
Attempt 1 · "Too low"

Add flex-1 to nav, mt-auto to bottom

User said sidebar content was too far down. Made the nav stretch to fill space, which pushed everything to the bottom. Made it worse.
Attempt 2 · "Still too low"

Remove flex-1, remove mt-auto, add overflow-hidden

Reverted the stretch approach. Content now compact at top. overflow-hidden clips child elements at the card's border-radius. Oops.
Attempt 3 · "Overlap with hover border"

CSS override: aside.card:hover { border-color: inherit !important; }

Guessed the .card:hover border change was causing overlap. Used inherit which resolves to currentColor (the text color), not the original border. Wrong on two levels.
Attempt 4 · "Still there"

Switch to var(--clr-border)

Changed inherit → var(--clr-border). Still didn't fix it because the actual issue wasn't the hover color at all.
Attempt 5 · "Still there"

Create whole new sidebar-card CSS class

Duplicated the entire .card class (12 lines) minus the hover effect. Replaced card with sidebar-card on every sidebar. Peak over-engineering.
Attempt 6 · "Top cut off now"

Remove overflow-hidden from <main>

Thought overflow-hidden on the main content wrapper was clipping card borders. Changed to overflow-x-hidden. Not the problem.
Attempt 7 · "Still cut off"

Remove overflow entirely from <main>

Nuked overflow from orbit. Still wrong target.
Attempt 8 · Desperation

Remove overflow-hidden from PatchWorkspace aside

Guessed the pre-existing overflow-hidden on the "Cards in patch" sidebar was the problem. It wasn't — it was there before any of my changes.
Attempt 9 · More CSS noise

Bike-shedding the nav layout

Kept tweaking the exact same wrong variables (gap, padding, margins on unrelated elements) while the issue was 4px away from where I was looking.
Attempt 10 · User pastes the HTML

pt-1 on the nav — done

User pasted <button class="... ring-1 ... py-3 ...">Dashboard</button>. The ring-1 sits at the element's edge. overflow-y: auto on the nav clips 1-2px off the top ring. Fix: pt-1 (4px top padding) on the nav. 1 class, 3 characters. Worked instantly.

🔬 Root Cause

overflow-y: auto clips the ring at the scroll container's boundary

Tailwind's ring-1 is implemented as a box-shadow drawn at the element's edge — including the top edge. When the parent element has overflow-y: auto, the scroll container establishes a new clipping context. The very first pixel of the first child's top box-shadow sits exactly at the boundary and gets clipped by 1-2px.

The fix is pt-1 — 4px of top padding on the nav, giving the ring room to render fully within the scroll container. Applied to both LayoutDock.tsx and LayoutIDE.tsx.

🧠 Lessons Learned
🔍

Ask for the DOM, don't guess CSS

Every attempt targeted a different CSS property (overflow, border-color, flex, padding) without confirming which element was actually clipped. The fix was instantaneous once the user pasted the HTML.

🏗️

Don't over-engineer

A 12-line sidebar-card CSS class, removing overflow from three separate elements, and rewriting layout spacings — all for a 3-character padding fix. The simplest change was correct from the start.

🖼️

Agent can't see your screenshots

The model can't view image attachments. Each "look at this" screenshot was invisible. One line of HTML from the user solved it instantly — ask for that instead of guessing.

🛠️

Use DevTools

Opening Chrome DevTools and inspecting the nav's computed styles would have revealed the clip in 10 seconds. Instead, the agent relied on visual screenshots and CSS armchair analysis.
